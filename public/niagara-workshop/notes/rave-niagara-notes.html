Chapter 1

Niagara basics

Creating the system and the main editor panels. The stack is explained on the first emitter.

  1. Create the systemchange

    • In Content/VFX/Fireworks right click FX›Niagara System
    • In the dialog click Create Empty Niagara System at the bottom left (no emitter from the grid)
    • Name it NS_Fireworks, double click to open

    Why: the system is the asset you later place in the level. It is only a container; the particles come from emitters inside it. Prefix NS_ means system, NE_ means emitter. Each emitter makes exactly one kind of particle, which is why our fireworks need five of them.

  2. The system nodeshow only

    • Look at the blue node: “this is the system itself”
    • Click System State, show Loop Behavior Infinite and Loop Duration 5.0. Change nothing
    • Look at User Parameters: “the knobs, we fill them later”

    Note: the system node has a small stack of its own that runs once for the whole effect, above all emitters. System State is the clock of the whole effect: it runs forever in five second rounds. Properties, System Spawn and System Update exist, but we do not need them today.

  3. Editor panelsshow only

    • Look at System Overview (centre), Preview (top left), Details (right)

    Note: System Overview is where the nodes sit. Preview is the live simulation. Details shows the settings of whatever you clicked; every value today is typed there.

Key idea

“An emitter is a recipe. Emitter Update says how many particles to make. Particle Spawn describes a newborn particle. Particle Update describes what happens to it every frame until it dies. Render says what it looks like. Everything we do today is adding one line to one of those sections.”

Chapter 2

Rocket

The rocket emitter, built from an empty template: rockets that fan out, slow down and shrink near the top. This block needs the full time.

  1. Add an empty emitterchange

    • Right click an empty spot in System Overview › Add Emitter
    • Type minimal into the search, pick Minimal (not one tagged Lightweight), create
    • Select the node, press F2 (or double click the name bar), rename to NE_Rocket
    • If the node has an Event Handler group: delete it with its bin icon

    Why: starting from the minimum means every module in the stack is one we added ourselves and can explain. Searching avoids the long template list; “empty” only finds CompletelyEmpty, which is not what we want. The rocket only sends messages later, it never listens, so it needs no event handler.

    You should see: a new node NE_Rocket next to the system node, header 0 particles.

  2. Card revealin the tool

    • Reveal card: Emitter State
    • Reveal card: Initialize Particle
    • Reveal card: Particle State
    • Reveal card: Sprite Renderer

    Emitter State: Emitter State decides when this emitter is alive and when it stops.

    Initialize Particle: Initialize Particle sets the starting values of every new particle: lifetime, colour, size and position.

    Particle State: Particle State ages each particle and kills it when its lifetime is over.

    Sprite Renderer: Sprite Renderer draws each particle as a camera-facing square.

  3. Contents of the empty emittershow only

    • Look at the four modules, nothing to click
    • Explain the four groups they sit in, top to bottom (cards below)
    Emitter Updateruns every frame, once for the emitter: is it alive, how many particles to make
    Particle Spawnruns once per newborn particle: lifetime, colour, size, first push
    Particle Updateruns every frame for every living particle: forces, movement, change over age
    Renderturns particles into pixels

    Note: every frame, Niagara runs these groups top to bottom. A module in the wrong group runs at the wrong time: a push in Particle Spawn happens once, the same push in Particle Update sixty times a second. The other rows of the node get explained when we use them.

    Emitter State
    decides when the emitter is alive
    Initialize Particle
    birth values, currently a lifetime of 5.0
    Particle State
    ages each particle and kills it when its lifetime is over
    Sprite Renderer
    draws each particle as a camera-facing square

    You should see: nothing, and the node header says 0 particles. Why? nothing in the stack says “make particles”.

  4. Emitter Stateshow only

    • Click Emitter State
    • Look at Life Cycle Mode and Scalability Mode: both already System. Change nothing

    Why: the emitter follows the system clock from the system node (Infinite, 5 seconds) instead of having its own. One place controls the whole show.

    System or Self? System means the emitter follows the system’s clock, Self gives it its own. Switch to Self once to show the extra loop rows that appear, then back to System.

  5. Card revealin the tool

    • Reveal card: Spawn Rate

    What it does: Spawn Rate creates a steady stream of new particles, a set number per second.

  6. Spawn Ratechange

    • + next to Emitter Update › search and add Spawn Rate
    • SpawnRate 3.0

    Why: Emitter Update runs once per frame for the whole emitter, so this is the tap: three rockets per second, evenly spaced.

    You should see: white dots appearing at the origin and sitting still for five seconds. First visible result; let it land.

  7. Card revealin the tool

    • Reveal card: Add Velocity
    • Reveal card: Solve Forces and Velocity

    Add Velocity: Add Velocity gives each new particle a push: a speed and a direction, usually once at birth.

    Solve Forces and Velocity: Solve Forces and Velocity adds up all forces and actually moves the particle. Keep it below every force.

  8. Add Velocitychange

    • + next to Particle Spawn › add Add Velocity (below Initialize Particle)
    • A yellow warning about Solve Forces and Velocity appears: click Fix issue
    • Leave all its values as they are for now
    Fix issue
    adds Solve Forces and Velocity to Particle Update. Add Velocity only sets a speed; Solve is the module that actually moves the particle.

    Why now: the dots move for the first time. Every following step in this block changes something you can see.

    You should see: the dots drift slowly in one direction instead of sitting still.

  9. Initialize Particlechange

    • Click Initialize Particle
    • Lifetime Mode Direct Set
    • Lifetime: arrow on the right › Random Range Float, Minimum 1.5, Maximum 2.5
    • Color Mode Direct Set
    • Click the colour swatch: pick a strong pink, then raise V (Value) well above 1, for example 5
    • Sprite Size Mode Uniform
    • Uniform Sprite Size: Random Range Float, Minimum 3.0, Maximum 5.0
    Random lifetime
    each rocket lives a different time, so they burst at different heights
    Color
    every rocket gets this colour; the default sprite material already uses particle colour, so no material work today
    V above 1
    colour values above 1 are brighter than white. Unreal’s bloom turns them into a glow; at 1 or below the rocket looks like a flat dot. This is why fireworks in Niagara glow. A big pink haze in the preview is bloom or lens flare, not a bug: the eye icon in the preview toolbar can switch Lens Flares or Bloom off
    Uniform size
    one number for width and height: round dots of slightly different sizes
    The arrow
    every input has one on its right. It turns a typed number into something smarter, like a random range or a curve. You use it many times today

    Why here: Particle Spawn runs once per particle, at birth. Everything a particle is born with lives here.

    You should see: glowing pink dots of different sizes, popping out after 1.5 to 2.5 seconds instead of five.

  10. Set up the launchchange

    • Click Add Velocity
    • Velocity Mode In Cone
    • Velocity Speed: Random Range Float, Minimum 3000.0, Maximum 4000.0
    • Cone Axis 0, 0, 1
    • Cone Angle 45.0
    Speed
    centimetres per second: 30 to 40 m/s straight out of the tube
    Cone Axis
    the default does not point up; 0, 0, 1 is straight up, Z is up in Unreal
    Cone Angle
    rockets fan out up to 45° from vertical

    Why here: the launch is a single push at birth, so it belongs in Particle Spawn. Ask: what would happen in Particle Update? (The push would be added every frame and the rockets would never stop accelerating.)

    You should see: dots flying up in a wide fan in straight lines, no arc yet. They shrink to a few pixels as they get far away, which is correct: zoom out with the mouse wheel until the whole fan fits.

  11. Card revealin the tool

    • Reveal card: Gravity Force

    What it does: Gravity Force pulls particles in one direction, downwards by default, like real gravity.

  12. Gravity Forcechange

    • + in Particle Update › add Gravity Force
    • If it lands below Solve Forces and Velocity: drag it above Solve
    • Keep Gravity at 0, 0, -980

    Why: 980 cm/s² is real gravity. The rocket is the heavy object of the show and keeps full gravity; the light sparks get a softer value later. Force modules only add to a running total of forces; Solve, which the fix-issue button added, turns that total into movement. That is why every force sits above Solve.

    You should see: the rockets now arc and fall back down.

  13. Card revealin the tool

    • Reveal card: Drag

    What it does: Drag is air resistance: it slowly takes speed away, so particles lose momentum and stall.

  14. Dragchange

    • Add Drag, place it below Gravity Force and above Solve
    • Tick both boxes, both 1.0

    Why: air resistance. A drag of 1 removes speed fast, so the rockets stall near the top of their flight, which is exactly where we want them to burst. The second box, Rotational Drag, only matters for spinning particles; our dots do not spin, so it changes nothing.

    You should see: the rockets slow down sharply and hang near the top of their flight before they pop out. They no longer fall far.

  15. Card revealin the tool

    • Reveal card: Scale Sprite Size

    What it does: Scale Sprite Size changes the sprite size over the particle’s life with a curve, so it grows or shrinks.

  16. Scale Sprite Sizechange

    • + next to Particle Update › add Scale Sprite Size, drag it directly below Particle State
    • Scale Sprite Size Mode Uniform Curve
    • Curve: three keys (time, value) 0, 0 0.1, 1 1, 0
    • Select all three keys, press 1 for smooth tangents
    • Uniform Curve Scale 2.0
    Setting keys
    add a key by right clicking the red line › Add Key (or middle click it, or the plus button below the curve). Click a key and type time and value into the two Key Data fields. Shortcut: the hill icon in the Templates row gives 0, 1, 0 at once; then move the top key to 0.1
    Key 1
    makes the curve ease in and out instead of having sharp corners.
    Curve Index
    already PARTICLES NormalizedAge. The green pill means a value every particle has its own copy of. NormalizedAge is 0 at birth and 1 at death, whatever the lifetime, so one curve fits every particle
    The curve
    the rocket grows in during the first tenth of its life instead of popping in, then shrinks to nothing exactly when it dies, so it never blinks out
    Scale 2.0
    multiplies the whole curve: at its peak the sprite is twice its birth size

    You should see: the rockets grow quickly after launch and shrink to nothing at the top instead of popping out. Zoom in to see it clearly.

  17. Check the ordershow only

    • Particle Update top to bottom: Particle State, Scale Sprite Size, Gravity Force, Drag, Solve Forces and Velocity
    • is Solve at the bottom everywhere? (Anyone who never saw the fix-issue prompt adds Solve now.)

    Note: Solve must sit below every force; a force placed under it is ignored until the next frame. Forces collect, Solve moves.

    You should see: rockets arcing up in a fan, slowing near the top, shrinking away. Tiny dots at scale 2.0 are correct: 3 to 10 cm sprites seen from 20 to 30 m away. The trails later make the rockets readable.

  18. Savechange

    • Save: Ctrl+S
Checkpoint

Check: pink rockets in a 45° fan, arcing, slowing, shrinking away near the top. Typical misses: Add Velocity in Particle Update (rockets accelerate forever), Solve above Gravity or Drag, Lifetime still at 5.0, Cone Axis left at another value.

Extra task A

Work in a duplicate: right click NE_Rocket › Duplicate, untick the original while you try, delete the copy afterwards.

  2. Launch from a line. Add Shape Location to Particle Spawn, above Add Velocity, Box Size 600, 0, 0. The rockets now start side by side instead of from one point.
Chapter 3

Events: blast

One emitter sends an event when its particles die; a second emitter receives it and spawns sparks at that position. This pattern is used throughout the course.

Key idea

“Emitters cannot see each other’s particles. The only way they talk is an event: a particle writes a small note, ‘I died here’, into a list. Another emitter reads that list and reacts. So that every note has a sender, each particle needs a fixed name tag. That is what persistent IDs are.”

  1. Card revealin the tool

    • Reveal card: Generate Death Event

    What it does: Generate Death Event sends a message to other emitters when a particle dies, including where it died.

  2. Generate Death Eventchange

    • NE_Rocket, Particle Update: add Generate Death Event at the very bottom, below Solve (and below Particle State)
    • Show the error that appears, and the rockets disappearing. Read the message out loud

    Why: every rocket will write a note with its last position when it dies. It sits at the bottom so the note contains the final position of this frame; above Particle State it is ignored. The error says roughly: before the Particle ID can be used, Requires Persistent IDs has to be activated. The note needs a sender, and the sender needs a name tag.

  3. Persistent IDs on the rocketchange

    • NE_Rocket: click the Properties row at the top of the node
    • Tick Requires Persistent IDs, save
    • Look at Sim Target: CPUSim, leave it

    Why: the Properties row holds settings of the emitter itself, not of its particles. Persistent IDs give every rocket the same ID for its whole life, and events carry that ID. Events only work on the CPU, so Sim Target must stay CPUSim.

    You should see: the error is gone and the rockets are back. Otherwise no change: nobody is listening yet.

  4. A second empty emitterchange

    • Add Emitter › Minimal, rename to NE_Blast
    • Do not add a Spawn Rate

    Why no Spawn Rate: this emitter must not make particles on its own schedule. It only makes them when a rocket dies. The event does the spawning.

    You should see: a second node NE_Blast, 0 particles, nothing new in the preview. We connect it before we shape it, so the next steps show results right away.

  5. The event handlerchange

    • NE_Blast node, top right: + Stage › Event Handler (or use the empty one if the template has it)
    • Click Event Handler Properties
    • Source Emitter: "NE_Rocket" Event: "DeathEvent"
    • Execution Mode Spawned Particles
    • Max Events Per Frame 0
    • Spawn Number 100
    Event Handler
    the part of an emitter that reacts to other emitters
    Source
    which list of notes to read
    Spawned Particles
    each note creates new particles
    Max Events 0
    no limit: every rocket that dies gets its blast
    Spawn Number
    a hundred sparks per dead rocket

    You should see: still nothing. The handler knows which notes to read, but not what to do with them.

  6. Card revealin the tool

    • Reveal card: Receive Death Event

    What it does: Receive Death Event reads death messages and copies chosen values, like position, onto the new particles.

  7. Receive Death Eventchange

    • + of the Event Handler group › add Receive Death Event
    • Keep its defaults. Look at three rows: Position Apply, Velocity Output, Color Output

    Note: each row says what happens with the rocket’s data. Apply writes it onto the new spark, Output leaves the spark’s own value alone.

    Position Apply
    sparks appear exactly where the rocket died
    Velocity Output
    sparks do not inherit the rocket’s leftover speed, so the blast stays centred
    Color Output
    sparks do not take the rocket’s pink; they stay white

    You should see: a big clump of white dots at the top of every rocket path, hanging still for up to five seconds, the template’s default lifetime. They have a place but no push.

  8. Add Velocitychange

    • NE_Blast, + of Particle Spawn › add Add Velocity
    • The Solve warning appears again: click Fix issue
    • Velocity Mode From Point
    • Velocity Speed Random Range Float 400.0 / 600.0
    • Velocity Origin stays ENGINE EMITTER SimulationPosition
    Grey ENGINE pill
    a value Unreal provides, here the position of the emitter

    Why it works: for an event spawn Niagara runs Particle Spawn first and the event handler afterwards. So every spark is born at the emitter’s position, right on top of the velocity origin, and Add Velocity gives it a speed in a random direction. Only then does Receive Death Event move it to where the rocket died. A hundred sparks with random directions: a sphere.

    You should see: the first real firework.

  9. Initialize Particlechange

    • Lifetime Mode Direct Set, Lifetime Random Range Float 1.5 / 2.5
    • Color Mode Unset
    • Sprite Size Mode Uniform, Random Range Float 3.0 / 5.0
    Color Unset
    the sparks keep the default white; the pink of the show comes from the trails and the light
    Same numbers
    as the rocket, on purpose: after this block both get replaced by one shared knob

    You should see: the sparks get smaller and die after 1.5 to 2.5 seconds instead of five.

  10. Particle Updatechange

    • NE_Blast, Particle Update: below Particle State and above Solve, add in this order:
    • Scale Sprite Size: Uniform Curve, keys 0, 0 0.1, 1 1, 0, keys smooth with 1, Uniform Curve Scale 2.0 (or right click the rocket’s module, Copy, then Paste here)
    • Drag: both boxes 1.0
    • Gravity Force: 0, 0, -200
    • Solve Forces and Velocity stays last

    Why: same reasoning as the rocket. Sparks pop in, expand, slow down, sink a little, and shrink to nothing instead of vanishing. Gravity is softer than the rocket’s because sparks are light.

    You should see: sparks pop in, spread into a sphere that slows down and hangs, sink a little, and shrink away. From far away a blast reads as a soft white ball.

  11. Debugging toolsshow only

    • Click the small person icon at the top left of the NE_Blast node (isolate): only the blasts play. Click it again
    • Untick the checkbox next to Drag in NE_Blast: the sparks fly much further. Tick it again

    Why now: with two emitters in the preview it is the first time you need to look at one of them alone. Isolating an emitter and switching modules off from the bottom up are the two fastest ways to find out what is wrong later.

    You should see: with isolate, the rockets vanish and the blasts appear on their own at the top; without Drag, the spheres grow much larger.

  12. Place the system in the levelchange

    • Save the system (Ctrl+S)
    • Drag NS_Fireworks from the Content Browser into L_Fireworks, onto the floor
    • Look at it in the viewport, or press Play and look up

    Why now: the preview is a black box without bloom. In the night level the same blast glows against the sky and finally looks like a firework. This is the payoff of the events block. The placed actor reads the asset, so every later change in the system shows up here too after saving.

    You should see: rockets rising from the floor and bursting into glowing white spheres against the night sky.

Checkpoint

Check: rockets rise, each one bursts into a white sphere near its apex, sparks slow, sink and shrink away. Most common reasons it fails, in order: Persistent IDs off on the rocket, Source in Event Handler Properties left empty, Receive Death Event missing, Add Velocity added inside the handler instead of Particle Spawn, Spawn Number still 0.

Chapter 4

User parameters

The values that rocket and blast share become user parameters on the system, so colour, size, lifetime and gravity can be changed in one place.

  1. Create user parameters from the rocketchange

    • NE_Rocket, on each input below: arrow on the right › Read from new User parameter
    • Initialize Particle: Lifetime Minimum
    • Initialize Particle: Lifetime Maximum
    • Initialize Particle: Color
    • Initialize Particle: Uniform Sprite Size Minimum
    • Initialize Particle: Uniform Sprite Size Maximum
    • Scale Sprite Size: Uniform Curve Scale
    • Gravity Force stays a typed 0, 0, -980, not linked
    What happens
    Niagara creates a user parameter with the right type, the current value and a name taken from the input, and links the input to it in one go. Nothing to type. That is where names like Minimum_Lifetime come from
    Rocket gravity
    the rocket keeps its own heavy gravity on purpose; the light things share a softer one

    Why: the same lifetime, size and gravity are used in several emitters. As soon as you want “a bit bigger”, you would hunt through every stack. A user parameter is one value that many inputs read. It is also visible on the placed actor in the level, so a level designer can tune the effect without ever opening Niagara.

    You should see: a blue USER pill on each of the six inputs, and six new rows under User Parameters on the system node. The preview looks the same.

  2. Link the blast inputschange

    • NE_Blast, link to the existing knobs (do not create new ones): arrow › Link Inputs › User › parameter
    • Initialize Particle: Lifetime Minimum › Minimum_Lifetime, Maximum › Maximum_Lifetime
    • Initialize Particle: Uniform Sprite Size Minimum and Maximum › the two size knobs (Color stays Unset)
    • Scale Sprite Size: Uniform Curve Scale › Uniform Curve Scale
    • Gravity Force: Gravity › Read from new User parameter (creates Gravity with 0, 0, -200)

    Why link instead of create: the blast must read the same knobs as the rocket. Creating them again from the blast makes duplicates such as Minimum_Lifetime1, and the two emitters drift apart. Gravity is the exception: the rocket has no gravity knob, so the blast creates it.

    You should see: USER pills on the five blast inputs and seven rows under User Parameters. The preview looks the same.

  3. Test the user parametersshow only

    • Change Uniform Curve Scale in User Parameters, watch rocket and blast grow together. Not Color: the blast ignores Color on purpose
    • Set them back

    Note: the eighth knob, for the ribbon width, comes with the rocket trail.

Chapter 5

Trails and light

The remaining three emitters: a ribbon trail behind each rocket, a light at each blast, and a ribbon trail behind each spark.

Rocket trail

  1. Card revealin the tool

    • Reveal card: Generate Location Event

    What it does: Generate Location Event sends a particle’s current position to other emitters, many times per second while it lives.

  2. Location events from the rocketchange

    • NE_Rocket, Particle Update: add Generate Location Event at the very bottom, below Generate Death Event
    • Event Type Send Rate, Event Send Rate 30.0

    Why: unlike the death event, which fires once, this one is a stream: every living rocket reports its position 30 times a second. Each report will become one point of the trail.

    You should see: no change. No error either, because the rocket already has persistent IDs. This is the only step of the trail without a visible result.

  3. New emitter and event handlerchange

    • Add Emitter › Minimal, rename to NE_RocketTrail. No Spawn Rate
    • + Stage › Event Handler
    • Source Emitter: "NE_Rocket" Event: "LocationEvent"
    • Execution Mode Spawned Particles, Max Events Per Frame 0, Spawn Number 1

    Why this order: we connect before we shape, so every following step shows its effect right away.

    You should see: still nothing behind the rockets. The handler knows which messages to read, but not what to do with them yet.

  4. Card revealin the tool

    • Reveal card: Receive Location Event

    What it does: Receive Location Event reads location messages and places each new particle where the sender was.

  5. Receive Location Eventchange

    • + of the Event Handler group › add Receive Location Event, keep defaults
    • Keep the Sprite Renderer for now

    Why: this module places each new trail particle where the rocket was when it reported. The sprites make the event visible: one particle per position report.

    You should see: a dotted line of white sprites behind every rocket, each dot a position the rocket reported. They stay up to five seconds, the template’s default lifetime.

  6. Card revealin the tool

    • Reveal card: Ribbon Renderer

    What it does: Ribbon Renderer connects the particles into one line instead of single dots.

  7. Ribbon Rendererchange

    • Delete the Sprite Renderer (bin icon)
    • + of Render › add Ribbon Renderer, leave its settings

    Why: a sprite renderer draws each particle on its own. A ribbon renderer connects the particles into one continuous strip, ordered by age. Nothing about the particles changed, only how they are drawn.

    You should see: the dotted lines turn into thin continuous lines behind the rockets. If a ribbon is black, set its Material to DefaultRibbonMaterial.

  8. Initialize Particlechange

    • Lifetime Mode Direct Set, Lifetime Random Range Float 0.5 / 1.2
    • Color Mode Direct Set, Color: arrow › Link Inputs › User › Color
    • Ribbon Attributes section: Ribbon Width Mode Direct Set, Ribbon Width Random Range Float 3.0 / 5.0
    Lifetime
    how long a trail point lives decides how long the trail is

    You should see: one change per line: the trails get shorter, turn pink, and get thicker.

  9. Card revealin the tool

    • Reveal card: Scale Ribbon Width
    • Reveal card: Curl Noise Force

    Scale Ribbon Width: Scale Ribbon Width changes the ribbon’s width over its life with a curve, so the trail tapers.

    Curl Noise Force: Curl Noise Force adds a random wobble to the push on every particle, so the trail is not a straight line.

  10. Particle Updatechange

    • Particle Update, below Particle State, add in this order:
    • Scale Ribbon Width: Ribbon Width Scale arrow › Float from Curve, keys 0, 1 1, 0 keys smooth with 1, CurveIndex NormalizedAge; Scale Curve: type 2.0, then arrow › Read from new User parameter
    • Gravity Force: Gravity › Link Inputs › User › Gravity (accept the fix-issue prompt if it appears)
    • Drag: both boxes 1.0
    • Curl Noise Force: Noise Strength 75.0, Noise Frequency 20.0
    • Solve Forces and Velocity at the bottom
    • Save: Ctrl+S
    Ribbon width curve
    old points get thinner, so the trail tapers to a point
    Gravity
    the smoke sags gently
    Curl Noise
    a swirling force field that makes the trail wobble like real smoke

    You should see: first the trails taper to a point, then they sag a little, then they start to wobble like smoke.

  11. Ribbon ID demoshow only

    • Receive Location Event: set Ribbon ID to Output for a moment, look, then back to Apply

    Note: a ribbon connects every particle that shares a Ribbon ID. With Apply, each trail point takes its ID from the rocket that sent it, so the points of one rocket form one ribbon. Reference

Summary

The finished system, the main concepts, and the settings of each emitter for comparing your work with the finished system.

Key concepts

The stack runs top to bottom

Properties, Emitter Spawn and Update, Particle Spawn and Update, Event Handler, Render. Birth values go in Particle Spawn, anything that changes over time in Particle Update. The wrong group means the wrong timing.

Forces collect, Solve moves

Gravity, Drag and Curl Noise only add to a total. Solve Forces and Velocity turns that total into movement, so it always sits below them.

Age drives change

Curves over NormalizedAge (0 at birth, 1 at death) let sprites grow in and shrink out, ribbons taper and lights fade, whatever the lifetime.

Emitters talk through events

A Generate module writes notes, an Event Handler with a matching Receive module reads them. CPU only. Persistent IDs give every note a sender.

Apply or Output

In a Receive module, Apply copies the sender’s value onto the new particle, Output leaves the particle alone. Position Apply places the blast, Ribbon ID Apply keeps one ribbon per rocket.

User parameters are the knobs

One value read by many inputs, visible on the placed actor. Change the look without opening the stack.

Troubleshooting

“Create Empty System” or the Minimal template cannot be found

In the Niagara System dialog the empty system is a button at the bottom left, not a tile in the grid. When adding an emitter, type minimal into the search; “empty” only finds CompletelyEmpty.

A value cannot be typed in

An editor running in German expects a decimal comma: 1,5 instead of 1.5.

The night level is too bright, or the picture flickers with every explosion

Automatic exposure. Add the Post Process Volume from the preparation: Infinite Extent on, Min and Max EV100 set to the same value.

Nothing shows in the preview

No Spawn Rate on the rocket, no renderer, or the node checkbox in the header is unticked. Check the Niagara Log for a red compile error, usually an input that is linked to a user parameter that was renamed or deleted.

The rockets are tiny or barely visible in the preview

Normal. The sprites are a few centimetres and the rockets fly 20 to 30 metres away. Zoom out with the mouse wheel. The trails make the rockets readable later; in the level they also glow.

A big pink haze or blobs in the preview

Bloom or lens flare from colour values above 1, not a bug. Switch off Lens Flares or Bloom with the eye icon in the preview toolbar, or lower V of the colour. In the level, Lens Flares › Intensity 0 in the Post Process Volume.

A key cannot be added to a curve

Right click the red line › Add Key, middle click it, or use the plus button below the curve. Or pick a shape in the Templates row and move the keys. Select all keys and press 1 for smooth tangents.

A yellow warning about Solve Forces and Velocity

A force module sits below Solve, or Solve is missing. Click the fix button in the warning, or drag Solve to the bottom of the force group.

Particles never die, the count climbs forever

Particle State is missing from Particle Update, or Kill Particles When Lifetime Has Elapsed is off. Add or tick it.

Rockets accelerate forever and leave the screen

Add Velocity sits in Particle Update instead of Particle Spawn. Drag it up into Particle Spawn.

The blast never appears

In order of likelihood: Source in Event Handler Properties is empty or points at the wrong event; Receive Death Event is missing from the handler; Spawn Number is 0; Generate Death Event is missing or disabled on the rocket; an emitter was switched to GPU. Max Events Per Frame 0 is correct, it means no limit.

The blast appears but the sparks all fly upward, not in a sphere

Velocity Origin was changed, or Add Velocity was placed inside the event handler, after the position was moved. Put Add Velocity back in Particle Spawn with the default origin.

The sparks drift sideways with the rocket

Velocity in Receive Death Event is set to Apply. Set it to Output.

Ribbons draw a fan of lines between rockets

Ribbon ID in Receive Location Event is not on Apply, or the rocket has Requires Persistent IDs off. Fix both. If it works in the Niagara preview but not on the actor in the level, save, delete the placed actor and drag a fresh one in from the Content Browser; also check the Outliner for a second, older actor.

The rockets disappear after adding an event module, with a Persistent IDs error

Expected: tick Requires Persistent IDs in the Properties row of the emitter that sends the event.

Generate Death Event seems to do nothing

It must sit below Particle State, best at the very bottom of Particle Update.

The ribbon is black

The Ribbon Renderer has no material. Set Material to DefaultRibbonMaterial.

A module looks different on your screen

Modules have versions, and an older or newer version can show other rows. Compare the version in the module’s dropdown or the version note at its top with yours.

User parameters with names ending in 001

A knob was created twice, usually because “Read from new User parameter” was used on the blast instead of Link Inputs. Relink the input first (arrow › Link Inputs › User › the original name), then right click the 001 parameter › Delete. Deleting first breaks the input that still uses it.

Only the rocket reacts when changing a knob

For Color that is correct: the blast ignores Color by design. For anything else, the blast input is not linked to the knob, or linked to a 001 duplicate. Check for the blue USER pill with the right name.

Changes in Niagara do not show up in the level

Save the system (Ctrl+S) or click Apply in the Niagara toolbar. If the effect stands still in the level viewport, Realtime is off: Ctrl+R in the viewport.

The light does nothing

There is no surface near the blast, so test in the level. Then check Light Attributes Radius is Apply, the Radius Binding is PARTICLES LightRadius, and Radius Scale is 25.

The light is far too bright

Light Renderer: lower Diffuse Scale and Specular Scale first (try 0.5 to 1.0), then Radius Scale. Do not lower V of User.Color, that dims rockets and trails too.

The effect vanishes when the camera turns away from the launch point

The fixed bounds are too small for an effect that is many metres tall. Select the emitter, use the toolbar’s Bounds › Set Fixed Bounds while the show is running, or type a larger box in Properties.

The preview stutters

Look at the particle counts in the node headers. NE_BlastTrail is usually the culprit. Switch it off with its node checkbox, or lower Spawn Number in NE_Blast.

Something was deleted or changed by accident

Ctrl+Z works in the Niagara editor too, also for deleted modules. If the history does not reach back far enough, see the next entry.

You are lost and the stack is a mess

Isolate the emitter, switch modules off from the bottom up until something sensible shows, then switch them back on one at a time. If that takes longer than three minutes, delete the emitter and rebuild it from this guide and the settings tables above; it is faster and you learn more.

Chapter 3

Collision

Drops hit the floor and the cubes and disappear there. Then they report each hit as an event.

  1. Card revealin the tool

    • Reveal card: Collision

    What it does: Collision checks each particle’s movement against the level and lets it bounce, stop or die on a hit.

  2. Collisionchange

    • NE_Raindrops, + Particle Update › Collision
    • Drag it to the very top of Particle Update, above Particle State
    • Look at CPU Collision Type Ray Traced and Sim Target CPUSim
    • Save, look at the level

    Why: Collision traces a short ray along each particle’s movement every frame and checks whether it would hit the level. On the CPU it uses the level’s normal collision, the same that stops a player walking through a wall.

    Key point: Niagara has no idea what the level looks like. Collision is the module that asks. The preview shows no change, because it has no world to ask.

    Position: at the very top works in 5.8. If 5.8 shows a warning about its position, follow the warning.

    You should see: in the level, drops stop at the floor and on top of the cubes. With the default Restitution of 0.6 they bounce and pile up as dots. Under the big cube it stays dry.

  3. Kill on collisionchange

    • Collision, section Kill Particles: tick Kill On Collision, value 1

    Why: a raindrop that hits something is over. Killing it removes the bouncing dots and keeps the particle count low, which matters with 800 drops a second.

    You should see: drops vanish the moment they touch a surface. The particle count in the node header drops sharply.

  4. Card revealin the tool

    • Reveal card: Generate Collision Event

    What it does: Generate Collision Event sends a message to other emitters when a particle hits something, including where.

  5. Generate Collision Eventchange

    • NE_Raindrops, Particle Update: add Generate Collision Event at the very bottom, below Solve

    • If the Persistent IDs error appears and the rain disappears: what is missing?

    Why: the death event of the rocket said “I died here”. This one says “I hit something here”. It needs a Collision module above it, otherwise there is nothing to report.

    You should see: no visible change. Nobody listens yet.

Summary

The finished system, the main concepts, and the settings of each emitter for comparing your work with the finished system.

Key concepts

Start somewhere

Simulation Position plus Position Offset starts particles five metres above the actor, wherever it stands. Shape Location spreads them over a box around that point.

Streaks, not dots

Non-Uniform size makes a sprite long and thin; Velocity Aligned turns its long side along the movement, so it leans with the wind.

Speed limit from Drag

Gravity speeds a particle up, Drag slows it in proportion to its speed. Where they balance, the drop falls at a steady speed.

Collision asks the level

Only the Collision module knows the world exists. It works in the level, not in the empty preview, and on the CPU it uses the level’s normal collision.

A third event

Generate Collision Event, Event Handler, Receive Collision Event: the same three parts as death and location events.

Facing and material

Sprite Facing and Alignment gives a sprite a direction to face; Facing Mode Automatic uses it and the sprite lies flat. A particle material needs the Particle Color node to show colour and fade.

An emitter’s own clock

Emitter State with Life Cycle Mode Self lets one emitter loop on its own, with a random length for the lightning.

CPU talks, GPU counts

On the GPU the rain can be twenty times denser, but events stop working and the bounds must be fixed.

Rain comes with the player

Attached to the player pawn, the actor moves; drops already falling stay in the world, so nothing slides.

Reference

Troubleshooting

The drops fall through the floor

In the Niagara preview that is normal: there is no floor to collide with. In the level: Collision module missing or disabled, the system not saved (Ctrl+S), Sim Target switched to GPU, or the floor mesh has no collision. The Basic level floor has collision; an imported mesh may not.

The drops lie on the floor as dots, or bounce

Collision works, but the drops are not killed. In the Collision module, section Kill Particles, tick Kill On Collision.

The rain stays where it was when the actor is moved

Initialize Particle has Position Mode Direct Set with 0, 0, 500: an absolute point in the world. Set Position Mode back to Simulation Position and tick Position Offset 0, 0, 500. The same for the lightning with 0, 0, 3000.

The drops are dots or squares, not streaks

Sprite Size Mode is still Uniform. Set Non-Uniform and 1.0, 20.0. If they are streaks but stand straight while drifting: Sprite Renderer Alignment Velocity Aligned.

No wind visible

Wind Force works through Drag: without a Drag module below it, the wind does nothing. Also check that Wind Force is above Solve and the user parameter Wind Speed on the system and on the placed actor is not 0.

The splashes never appear

In order of likelihood: looking at the preview instead of the level; Generate Collision Event missing on the drops; Source in Event Handler Properties empty or set to another event; Receive Collision Event missing; Spawn Number 0; Requires Persistent IDs off on the drops.

The splashes jump around and vanish after a moment

Execution Mode in Event Handler Properties is Every Particle, the template default. Every new hit moves all existing splashes. Set Spawned Particles. Same for NE_Circle and NE_Trail.

The splashes appear at the system’s origin, not where drops hit

Receive Collision Event is missing from the event handler, or its Position row is not Apply.

The splashes shoot into the floor

Velocity in Receive Collision Event is Apply, so the splash inherits the drop’s falling speed. Set it to Output. Also check the Cone Axis is 0, 0, 1.

The rings stand upright and turn with the camera

The checkbox in front of Sprite Facing is not ticked, the module is missing, or the Sprite Renderer’s Facing Mode was changed from Automatic. Automatic uses the facing vector as soon as the module writes one.

The rings flicker or are cut in half on the floor

They lie exactly in the floor surface. In M_Circle, connect a Constant3Vector 0, 0, 2 to World Position Offset; that lifts the rings two centimetres.

The new material shows as a grey checker or nothing on the particles

Particle materials need the usage flag Used with Niagara Sprites. Unreal usually sets it when the material is assigned and asks to recompile; open the material, check Details › Usage, tick it if needed, Apply and save.

The rings are white, black or square

The material: Blend Mode must be Translucent, Opacity must get the texture channel that holds the ring (R for white on black, A for a transparent background), and Apply must be clicked before saving.

The rings or splashes do not fade

Scale Color is missing or its Scale Alpha curve is flat. For the rings also check that the material multiplies by Particle Color alpha; without the Particle Color node the fade never reaches the pixels.

A User parameter called Color001

Color was created again in a second emitter instead of linked. Relink the input to Color (arrow › Link Inputs › User › Color), then delete Color001.

Trails connect drops in a fan of lines

Ribbon ID in Receive Location Event is not Apply, or the drops have Requires Persistent IDs off. Same fix as the rocket trail.

The floor is dry for a second when the level starts

Warmup Time on the system’s Properties is 0. Set 2.0.

The preview or the level stutters

Look at the particle counts in the node headers. Lower Spawn Rate first, then switch off NE_Trail; collision traces for thousands of drops are the expensive part.

The refraction does nothing

Refraction Method in the material is still None, the Normal pin is not connected, or the drops are too thin to see it: test with Sprite Size 10, 60. If the Refraction pin is greyed out, switch Shading Model to Default Lit.

The lightning is not visible

The level is too bright: lower the DirectionalLight. Then check Light Radius (8000), V of the colour, and that the Light Renderer exists. Judge it in the level; the preview has no floor to light.

The lightning flashes exactly every 5 seconds

Emitter State Life Cycle Mode is still System, so the emitter follows the system loop. Set Self, then the random Loop Duration and Recalculate Duration Each Loop.

The lightning is a steady light, no flicker

Alpha Scales Brightness is off in the Light Renderer, or Scale Color is missing. With it on, the Scale Alpha curve controls the brightness.

The GPU copy shows errors or nothing

Events do not exist on the GPU: delete Generate Collision Event and Generate Location Event in the copy. GPU emitters need Fixed bounds; with a box that is too small the rain disappears when its box leaves the screen.

The rain does not follow the player

The Level Blueprint was not compiled or saved, the reference points to a different actor (the deleted copy), or Location Rule is Keep Relative. In the editor viewport nothing moves; it only works in Play.

The rain slides sideways when the player moves

Local Space is on in the emitters. Rain must stay in world space; switch Local Space off.

Last session’s fireworks are still broken

Use the Session 1 summary tables and compare module by module. Most common: Execution Mode Every Particle, a missing Receive module, a user parameter with 001 at the end.

Embers

A second emitter of glowing streaks that shoot out of the smoke and rise. Almost everything is known, so you build most of it alone.

    Velocity

Light and level

A glow inside the smoke, the effect in the dark level, and two different smokes from one asset.

  1. Into the levelchange

    • Drag NS_Smoke into L_Smoke, onto the floor
    • System node › Properties: Warmup Time 5.0

    Why: the same reason as the rain: without warmup the column grows from nothing when the level starts. Smoke lives up to 8 seconds, so 5 seconds of warmup give an almost full column.

    You should see: the smoke standing on the floor, no hard line where it meets the floor (that is DepthFade). Fly close to check.

  2. A glow inside the smokechange

    • NE_SubUVSmoke, Render + › Light Renderer, next to the Sprite Renderer
    • Source Mode Emitter
    • Use Inverse Squared Falloff off, Affects Translucency on
    • Radius Scale 1.6, Color Add 80, 80, 80
    • Save, look in the level
    Source Mode Emitter
    one light for the whole emitter instead of one per particle. A hundred smoke lights would be expensive and flicker
    Radius
    nothing writes a light radius here, so the renderer uses its default of 100 (Epic’s reference); × 1.6 is about 1.6 metres
    Color Add 80
    added on top of the default colour, a very bright light
    Affects Translucency
    lights the Default Lit smoke from inside: this is why the material is lit

    Question: “In the fireworks the light needed Light Attributes. Why not here?” Light Attributes writes radius and brightness per particle. With Source Mode Emitter the renderer reads the Emitter values instead (see its Bindings: EMITTER LightRadius, EMITTER Color), and nothing writes them, so it uses its defaults: radius 100, white. Radius Scale and Color Add are the knobs that are left, which is why the reference sets Color Add so high.

    You should see: a pool of light on the floor around the base. The smoke itself still looks dark brown in the dim level, unlike in the preview; the next step fixes that.

  3. Glow from the materialchange

    • Open M_SubUVSmoke
    • Colour: the Multiply that feeds Base Color also goes into a new Multiply with B 1.5 › Emissive Color
    • Alpha: a Power node between the alpha Multiply and DepthFade, Exp 2
    • Apply, save, look in the level
    Why it looked dark
    the material is Default Lit: it shows only the light that reaches it. The preview has bright studio lights, the level is dim on purpose, and a 1.6 metre particle light cannot light a column several metres tall
    Emissive × 1.5
    the puffs now give off their own colour: young orange puffs glow in any level, old brown ones stay dark. They still react to the level light through Base Color. At 2 the overlapping puffs at the base clip to flat orange and lose the texture detail
    Power 2
    the emissive also brightens the faint, almost invisible edges of each picture, and the puffs turn blocky. Squaring the alpha pushes faint values to nothing and leaves dense smoke almost as it was

    You should see: in the level the same orange base and dark brown trail as in the preview, with soft edges.

  4. Material instance, if there is timechange

    • In M_SubUVSmoke replace the three numbers with parameters: hold S and click to add a Scalar Parameter, name it, set its default, wire it in
    • Emissive Strength 1.5 into the emissive Multiply, Alpha Power 2 into Power Exp, Fade Distance 20 into DepthFade FadeDistance

    • Content Browser: right click M_SubUVSmoke › Create Material Instance, name MI_SubUVSmoke
    • NE_Smoke, Sprite Renderer: Material MI_SubUVSmoke

    Why
    every change in the material needs Apply and a recompile. An instance only changes values, so the level updates while you drag
    Parameters
    only values that are parameters show up in the instance. The wiring stays in the parent material
    Shared

Key concepts

A flipbook is a film on a card

The texture holds 64 pictures. The renderer cuts it with Sub Image Size, the Sub UV module picks the picture over NormalizedAge, the material’s ParticleSubUV node reads and blends it.

Three parts must agree

Texture 8 × 8, renderer 8 × 8, module 0 to 63. Whole sheet, frozen picture or a jump each point to one of them.

Rising is just another force

Gravity with positive Z, or Acceleration Force: the solver does not care which. Drag turns it into a steady speed.

Soft sprites need order

Translucent sprites are sorted back to front with Sort Mode View Depth, faded near surfaces with DepthFade, and trimmed with a cutout to save overdraw.

One light for the emitter

Source Mode Emitter makes one light at the emitter instead of one per particle: cheap and steady.

No events, GPU is free

Smoke and embers never talk to each other, so they can run on the GPU with many more particles.

Troubleshooting

Every sprite shows the whole sheet of small pictures

The renderer does not know the grid. Sprite Renderer, section Sub UV: Sub Image Size 8, 8.

All puffs show the same picture and do not animate

Sub UVAnimation is missing, unticked, sitting in Particle Spawn instead of Particle Update, or its Lookup Index is not NormalizedAge.

“No Sprite Renderer selected” on the Sub UVAnimation module

In the module, Setup, expand Sprite Renderer (Sprite Renderer Info) and set the inner Sprite Renderer dropdown from None to the emitter’s Sprite Renderer. The module reads the grid size from it.

The animation jumps or shows an empty picture

End Frame Range Override is higher than 63, or Sub Image Size does not match the texture. Texture, renderer and module must all say 8 × 8 and 0 to 63.

The animation steps instead of flowing

Sub UV Blending Enabled is off on the renderer, or the material uses a plain Texture Sample instead of ParticleSubUV.

The smoke is a grey checker or does not show at all

The material was not applied or saved, or it lacks the usage flag Used with Niagara Sprites. Open it, check Details › Usage, Apply and save.

The smoke is black or very dark in the level

The material is Default Lit and the level is dim, so it shows only the little light that reaches it. Do the step Glow from the material: Base Color Multiply × 1.5 into Emissive Color. Still dark: check that the material was applied and saved.

The centre of the smoke is flat orange and you see the floor through it

Two causes. The spawn box sits half under the floor and Depth Fade makes the puffs near the floor see-through: Shape Location Offset Mode Default, Offset 0, 0, 50. And the emissive factor is too high, so overlapping puffs clip to one flat colour: lower it to 1.5 or 1.

Blocky or square edges around the puffs after adding emissive

The emissive makes the faint edges of each picture visible. Add a Power node with Exp 2 between the alpha Multiply and DepthFade, or lower the emissive factor to 1.

Square edges or a hard line where the smoke meets the floor

Square edges: Opacity is not wired from the texture alpha, or Blend Mode is not Translucent. Hard line: DepthFade is missing or its Fade Distance is 0.

Puffs jump in front of each other while the camera moves

Sorting: Sprite Renderer Sort Mode View Depth. If it still flickers, lower the Spawn Rate.

The smoke falls or does not rise

Gravity Force still has a negative Z. It must be 0, 0, 200. Also check that Solve sits below the forces.

Scale Sprite Size does nothing

Initialize Particle Sprite Size Mode is Unset: there is no size to scale. Set Uniform with a size.

The embers fall instead of rising

Gravity Force on NE_Sparks still has the default -980. Set 0, 0, 500, and check Acceleration Force is 0, 0, 500.

The embers are round dots, not streaks

Sprite Renderer Alignment is not Velocity Aligned, or Scale Sprite Size is not Non-Uniform with a longer Y.

The embers do not change colour or never fade

Most often: Initialize Particle Color Mode is still Unset. Scale Color multiplies the colour set at birth, so with nothing set the sparks stay white. Set Color Mode to Direct Set, white. Otherwise: Scale Color mode is not RGBA Linear Color Curve, or the alpha stops were set in the colour row of the gradient. Alpha is the lower row.

No glow from the light

Judge it in the level, not the preview. Check Source Mode Emitter, the Light Renderer’s checkbox, Color Add, and that the level is dark enough.

The GPU embers disappear when the camera looks up

The Fixed Bounds box is too small. Raise Max Z, or use the toolbar’s Bounds › Set Fixed Bounds while the effect runs.

The preview stutters

Big translucent smoke sprites cost more than many small particles. Lower Spawn Rate or Sprite Size first, check the cutout is on, and look at Shader Complexity in the level viewport.

Module cards, Fireworks (19)

  1. Emitter State: Controls the emitter itself (running, paused, finished), never single particles.
  2. Spawn Rate: Creates a steady number of particles per second.
  3. Add Velocity: Gives every new particle a direction and speed at birth.
  4. Solve Forces and Velocity: Turns all collected forces and velocities into real movement.
  5. Initialize Particle: Sets a particle’s basic values (lifetime, colour, size, mass).
  6. Particle State: Ages particles and removes them at the end of their lifetime.
  7. Sprite Renderer: Draws each particle as a flat image that faces the camera.
  8. Gravity Force: Pulls particles down, so the flight path becomes an arc.
  9. Drag: Slows particles down so they do not stay fast forever.
  10. Scale Sprite Size: Lets sprites grow or shrink over their life.
  11. Generate Death Event: Reports a particle’s death, with its data, to other emitters.
  12. Receive Death Event: Reads such a death message and takes over the data for new particles.
  13. Generate Location Event: Keeps reporting a particle’s position so others can follow it.
  14. Receive Location Event: Places new particles where the sender was.
  15. Ribbon Renderer: Connects the particles into one line instead of single dots.
  16. Scale Ribbon Width: Changes the ribbon’s width over its life with a curve, so the trail tapers.
  17. Curl Noise Force: Adds a random wobble to the push on every particle, so the trail is not a straight line.
  18. Light Renderer: Lets particles cast real light into the scene.
  19. Light Attributes: Writes light values (e.g. radius) onto particles so the Light Renderer can read them.

Module cards, Rain (8)

  1. Shape Location: Starts particles anywhere inside a shape instead of at one point.
  2. Wind Force: Pushes particles with wind plus turbulence.
  3. Collision: Detects contact with the environment, then bounce, slide or kill.
  4. Generate Collision Event: Reports an impact so another emitter can react.
  5. Receive Collision Event: Places new particles at the impact point.
  6. Scale Color: Multiplies colour and alpha over the life, for example to fade out.
  7. Sprite Facing and Alignment: Gives sprites their own orientation instead of facing the camera.
  8. Spawn Burst Instantaneous: Creates a fixed number of particles at once.

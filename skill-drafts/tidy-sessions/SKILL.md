# Tidy

Goal: show where every session stands, then archive every session whose work is **settled** and keep the rest. The user's request to tidy is their permission to archive every session that counts as settled below. The session itself can be restored (the Archived list, `unarchive_session`), but uncommitted changes in its worktree can be lost when it is archived, so the dirty check in step 3 is what protects the work (it does not see ignored files). With that check in place, decide per session yourself and do not ask first. If the user named a scope (a project, a title, "older than a day"), tidy only that scope. **Overview only:** if the user only asks for the state of their sessions or what would be archived (for example which sessions wait for an answer, have uncommitted work or should continue), run steps 0 to 5, call `archive_session` for nothing, and head group 5 "Would archive". If they ask about one group only, show that group in full and the others as counts.

A session is **settled** when nothing will happen in it any more and no question to the user is open. That means one of these:
- It ended with a final report that names no open question and no remaining step.
- It handed off to a successor session that is in the list and has taken over the remaining work (it names this session or its task).
- A result it named as pending has since landed (verified in step 3).
- A session with a later `lastActivityAt` says explicitly that it finished or replaced this session's work (obsolete).

A session is **live** when any of these holds:
- Its `pinned` field is true, or its `isRunning` field is true, or its last events contain a direct request for user input, approval or a decision that has not been answered yet.
- It is the parent of a live session (the parent is the session named in the child's `startedBy` field).
- It started the current session (its ID is the `parentSessionId` from the `get_session` call in step 1), because the current session is not in the list and its parent must not look childless.
- It waits for a result that has not landed yet.
- It has unmerged work: its branch exists and is not landed (step 3), whatever its last message says.

A session that matches a live condition is live even when it also matches a settled one. When the ending is unclear, for example an aborted session, keep it and name it under **Needs your attention**.

## Groups

The overview puts every session in the first group that fits:

1. **Waiting for you**: its last events contain a direct request for user input, approval or a decision that has not been answered yet.
2. **Working or waiting for a result**: its `isRunning` field is true, or it waits for a result that has not landed yet.
3. **Unmerged or uncommitted work**: its branch is not landed, its worktree is dirty, or a merge it claimed has not landed (all from step 3).
4. **Stopped, should continue**: it is not running and no question is open, but its last message names a remaining step, or its ending is unclear (for example aborted).
5. **Settled**: it matches a settled condition and no live condition. These are archived.

A parent kept only because of a child sits in that child's group, and its line says "parent of <title>". A session that started the current session sits in the group of its own state, and its line says so. A pinned session is never archived: if it is otherwise settled, group 5 lists it as "pinned, kept". **Needs your attention:** is the start of a line for a kept session with an open point or an unverified state (an unanswered question, a command only the user can run, a claim that turned out false, a git or branch problem, an unprotected current-session parent), followed by the exact question or issue.

## Steps

0. **Check the environment.** If `list_sessions`, `list_events`, `get_session` and `archive_session` are not available, say that this skill needs the Claude desktop app's Code tab, and stop. Done when the tools exist or you have stopped.
1. **Inventory.** Call `list_sessions` with `limit: 100` (it lists unarchived sessions by default and has no paging). If the result has exactly as many rows as the limit, call it again with limit 500, then with limit 1000, and stop as soon as a call returns fewer rows than its limit. If 1000 rows still fill it, the list may be cut off and a live child could be missing: treat the run as overview only (see the goal), call `archive_session` for nothing, and say so in the overview. Sessions the tools do not list (cloud sessions, sessions from the CLI or an editor) are not checked: say so in the report. Call `get_session` once with `session_id: "self"` and note the current session's ID and its `parentSessionId`. If that call fails or does not give the current session's ID, the current session's parent cannot be protected: treat the run as overview only, call `archive_session` for nothing, and name this under **Needs your attention**. Keep the complete result as the **full list** for every parent, child and successor check. From it build a separate **tidy list**: apply the user's scope to the tidy list only ("older than" means `lastActivityAt`), and leave out the current session (the list omits it, observed in the app; drop its row anyway if it appears) and every row whose `startedBy` is the current session. Rows left out of the tidy list stay in the full list. Done when both lists are written down.
2. **Read each ending.** Call `list_events` with `limit: 8` per session on the tidy list, in parallel batches of 10 sessions. If a call fails, keep that session and name it under **Needs your attention** with the error. Ignore `[result]` lines: they close every turn. For a session with no assistant message, retry that session once with `limit: 40`. If there is still none, or a user message or a pending approval comes after the last assistant message, keep the session and name it in the report. Done when each session has its last assistant message or is named in the report.
3. **Verify every candidate.** A candidate is a session that looks settled. Check each candidate, and each session whose last message claims a state ("integration running", "waiting for X", "merged"). A claim counts as landed only when git shows it, or a successor session reports the checked result (a commit, a command output) and does not just repeat the claim; without that it has not landed. For a session with a `branch` field, git decides: a successor's report never overrides a failed landed check below. A claimed merge that has not landed makes the session **live**. Check the successor session first, looking in the full list (it may be outside the scope). Then, when the session's folder still exists and is a git repo, check git. Every git command below, including the shortened ones, runs as `git -C "<folder>" ...`. If any git command fails with an error you did not expect, keep the session and name it under **Needs your attention** with the error:
   - Branch: the `branch` field of `list_sessions`, which only sessions in their own worktree have. A row without it works in the shared main folder: skip the branch, landed and dirty checks, judge it from the events and the successor only, and append "git not checked" to the archive reason. If `git -C "<folder>" rev-parse --verify --quiet refs/heads/<branch>` finds nothing, keep the session, write "branch not found, not verified" and name it under **Needs your attention**.
   - Default branch: `git symbolic-ref --quiet --short refs/remotes/origin/HEAD`, falling back to the first of `origin/main`, `origin/master`, `main`, `master` that `git rev-parse --verify --quiet` accepts. If none exists, keep the session and name it under **Needs your attention** as "default branch not found". Never run `git fetch`; say in the report when you used a local branch or a remote ref that may be stale.
   - Landed: if `<branch>` and `<default-branch>` are the same local branch (for example both are `main`), the test proves nothing: keep the session and name it under **Needs your attention**. Otherwise run `git merge-base --is-ancestor refs/heads/<branch> <default-branch>`: exit 0 means landed, exit 1 means not an ancestor, any other exit is an error. After exit 1, if `git rev-list --merges <default-branch>..refs/heads/<branch>` prints anything, keep the session and name it under **Needs your attention** as "merge history not verifiable" (`git cherry` ignores changes made inside a merge commit). Otherwise run `git cherry <default-branch> refs/heads/<branch>`: no line starting with `+` and no error means landed; any `+` line means not proven (a squash merge of several commits looks the same), so keep the session and name it under **Needs your attention** as "unmerged or squash merge not verifiable".
   - Dirty folder (only for a row with a `branch` field): if `git status --porcelain --untracked-files=all` prints anything, keep the session and name it under **Needs your attention**, because archiving can clean up its worktree.
   - If the folder is gone or is not a git repo, judge from the events only and append "git not checked" to the archive reason.

   Done when every candidate is marked settled or live, each with the observation it rests on (successor title, git result, open question or waiting condition).
4. **Sort into groups.** Put every session of the tidy list in its group. Decide the deepest children first, then their parents, up the whole `startedBy` chain. Before a session stays in group 5, look in the full list for rows whose `startedBy` is that session (rows left out of the tidy list count). If any of them is not settled, or is kept or out of scope, the parent goes into that child's group; archive a parent only when all its children are settled or already archived. Done when every session has a group and the observation it rests on.
5. **Show the overview.** One list, group by group in the order above, empty groups left out. One line per session: its title, the observation its group rests on (the open question, the running state, the git result, the remaining step, the successor) and, where it applies, a **Needs your attention:** line. Count every figure from this run's tool results. Add one line of notes when they apply: the list may be cut off, a possibly stale git ref was used, sessions the tools do not list were not checked. Show it before the first `archive_session` call. In overview only mode, end here.
6. **Archive the settled ones.** Never call `archive_session` for a session with `pinned` or `isRunning` true. Call it for all sessions of group 5 in one parallel batch with a short `reason`. Archiving a parent also archives its finished side sessions (sessions it started), and "already archived" is success. If a call fails because the session is open on screen (or was just pinned), do not retry: list it as kept. If it fails for another reason, retry it once, then list the session with the error text. Done when every group 5 session is archived or listed with its refusal.
7. **Report**, short, in the conversation's language, after the overview and without repeating groups 1 to 4. If nothing was archived, start with "0 sessions archived". Then: how many were archived (only sessions where `archive_session` succeeded in this run; "already archived" separately) as one line of titles, and each session of group 5 that was kept, with its refusal (open on screen, pinned: the user archives it from the sidebar).

Never archive the session you are running in, and never delete a session (`delete_session`).
